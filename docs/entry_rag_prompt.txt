│ L2. 레짐 엔진 (FlowEngine)                               │
│   - EMA, flow_score, 수급 점수 종합 → bias 결정          │
│     (LONG_BIAS / SHORT_BIAS / NEUTRAL)                  │
│   - 갱신 주기: 약 1~3초                                  │

│   - LLMPulse(10분): 큰 흐름 BULLISH/NEUTRAL/BEARISH      │
│   - 공통 한계: API 응답 3~5초 + 입력이 과거 틱 집계값    │
├─────────────────────────────────────────────────────────┤
│ L4. 진입 결정                                            │

│   - sim_trades: 시뮬레이션 체결 이력 (run_id, pnl_ticks, │

  - 엔진 BEARISH 감지: 13:35 → 12분 후행

구조적 원인:
  1. EMA는 N틱 평균 → 수렴 속도가 느림 (길수록 안정, 짧을수록 노이즈)
  2. flow_score는 누적 집계 → 방향 전환 직후에도 관성이 남음
  3. LLM은 과거 틱 요약을 입력받아 판단 → 분석 대상 자체가 후행
  4. 레짐 확정 = 진입 결정 구조 → 방향 확인 후 진입하면 항상 늦음

결과:
  - 추세 초반 진입 불가 (확인 전 진입 = 휩쏘 위험)
  - 추세 후반 진입 시 수익 구간 짧음
  - 레짐 신호가 맞아도 진입 타이밍이 나빠 수익이 안 남

분리 필요성:
  현재: [레짐(방향)] = [진입(타이밍)] → 둘 다 후행
  목표: [레짐(방향)] ≠ [진입(타이밍)]
        레짐은 "무엇을"   — 느려도 됨, 정확성이 목적
        진입은 "언제를"   — 빠른 마이크로 신호 기반

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

목적:
  레짐이 방향을 결정한 후, 실제 진입 타이밍을 미세 조정하는 시스템.
  "지금 진입해야 하나, 아니면 몇 초/틱 더 기다려야 하나?"를 판단.

입력 (진입 시점 직전 30~60초 마이크로 스냅샷):
  - volume_burst 변화 궤적
  - basis_ema_delta (선/현물 스프레드 변화 속도)
  - price_vs_vwap 이격 방향 및 크기
  - oi_delta (미결제약정 순변화)
  - fut_fgn_delta / fut_inst_delta (수급 delta 속도)
  - ema_fast_slope (단기 EMA 기울기)
  - flow_score 최근 N틱 기울기
  - 현재 session_phase (장초반/중반/후반)
  - 현재 레짐(bias), entry_signal 상태

예상 출력:
  - enter_confidence: 지금 진입 적합도 (0.0 ~ 1.0)
  - whipsaw_risk: 휩쏘 위험도 (0.0 ~ 1.0)
  - suggested_wait_ticks: 진입 전 추가 대기 권장 틱 수 (0 = 즉시)
  - pattern_label: 유사 과거 패턴 이름 (예: "volume_surge_confirm")

레이블 데이터 (학습 기반):
  - sim_trades.pnl_ticks: 해당 진입 이후 실제 손익
  - sim_trades.max_adverse_excursion: 진입 후 최대 불리 이탈폭
  - sim_trades.exit_reason: 왜 청산했는가 (sl/trail/시간)

RAG 방식 구상:
  - 과거 진입 패턴(마이크로 스냅샷 + 결과)을 벡터화하여 저장
  - 신규 진입 시점에서 유사 패턴 K개 검색 (코사인 유사도)
  - 검색된 K개의 pnl 분포, 휩쏘 비율로 enter_confidence 결정
  - LLM은 검색된 패턴 요약 + 현재 컨텍스트를 받아 최종 판단

[목차]

1. 진입 RAG의 필요성과 기대 효과
   - 기존 레짐 기반 진입의 구조적 한계 요약
   - Entry RAG 도입 시 기대되는 개선점 (정량적 가설 포함)
   - 도입하지 않을 경우 장기적 문제

2. 학습 데이터 설계
   - 어떤 데이터를 어떻게 레이블링할 것인가
   - 진입 직전 스냅샷의 적절한 시간 윈도우 (몇 초/틱이 최적인가)
   - 레이블 기준: pnl_ticks 절대값 vs 상대값 vs 결과 구간 분류
   - 클래스 불균형 문제 (수익 진입 vs 손실 진입 비율) 처리 방법
   - 최소 몇 건의 데이터가 필요한가 (학습 가능 임계량)

3. 피처 엔지니어링
   - 현재 regime_ticks에서 추출 가능한 피처 목록 및 우선순위
   - 시계열 피처 처리 방법 (롤링 통계, 기울기, 변화율)
   - 피처 정규화 전략 (일별 정규화 vs 글로벌 정규화)
   - 피처 중요도 사전 가설 (어떤 신호가 진입 타이밍에 가장 유효한가)
   - session_phase별 피처 가중치 차별화 필요성

4. RAG 아키텍처 선택
   - 옵션 A: 벡터 유사도 검색 (FAISS / ChromaDB) + LLM 요약
   - 옵션 B: 전통 ML 분류기 (RandomForest / XGBoost) — RAG 없이
   - 옵션 C: 하이브리드 (ML 스코어 + 유사 패턴 RAG 보완)
   - 각 옵션의 장단점, 운영 부담, MMEAN 환경 적합성 비교
   - 추천 방식과 이유

5. 구현 단계별 로드맵
   - Phase 0: 데이터 수집 및 레이블링 파이프라인 구축
   - Phase 1: 오프라인 백테스트 (regime_ticks × sim_trades 조인 분석)
   - Phase 2: 피처 중요도 분석 및 모델 학습
   - Phase 3: 온라인 통합 (EntryTimingEngine 모듈화)
   - Phase 4: A/B 테스트 (기존 진입 vs RAG 진입 비교)
   - 각 단계 예상 소요 기간 및 판단 기준

6. 주의사항 및 리스크
   - 과적합(Overfitting) 방지 전략
   - 시장 구조 변화(레짐 shift)에 대한 모델 갱신 주기
   - 진입 RAG가 오작동 시 폴백(fallback) 처리 방법
   - 레이블 데이터의 생존자 편향(survivorship bias) 문제
   - 소량 데이터(초기 수백~수천 건)에서의 한계

7. 성과 측정 지표
   - Entry RAG 도입 전/후 비교에 사용할 KPI 정의
   - whipsaw_risk 예측 정확도 측정 방법
   - enter_confidence 임계값 튜닝 기준
   - 언제 Entry RAG가 "작동하고 있다"고 판단할 수 있는가

8. 최종 추천 구현 구조
   - MMEAN 기존 구조에 Entry RAG를 통합하는 최소 침습적 설계
   - 새로 만들어야 할 모듈 목록 (파일명, 역할, 의존성)
   - DB 스키마 변경 사항 (신규 테이블/컬럼)
   - 기존 entry_gate (pattern_memory RAG)와의 역할 분담
