────────────────────────────────────────────────────────────────────────────────
심각도: 높음

  app_bootstrap.py 의 _run_rag_prep_if_stale()이 step2+4 만 실행.

  - rag_prep 헬스 패널에서 status=success 인데 pattern_memory=0 유지
  - entry_gate 가 실질적으로 항상 ALLOW
수정 방향:
  _run_rag_prep_if_stale() 에서 step 순서를 (1, 2, 4) 로 변경.
  또는 market_features 행 수를 staleness 판단 기준에 추가.
전제조건: 없음 (즉시 수정 가능)

[A-002] 게이트 효과 분석 + 정책 검증 리포트
────────────────────────────────────────────────────────────────────────────────
우선순위: 높음 (단, 데이터 축적 후) — 【A-003 Ambiguous v2 설계의 전제조건】
배경:
  entry_gate 임계값이 적절한지 감이 아니라 숫자로 확인해야 함.
  단순 "몇 번 발동했는지" 에서 "실제로 손실을 회피했는지" 로 나아가야 함.

  1단계 — 발동 빈도 집계:
    ALLOW/HALF/REJECT 비율, LLM positive → REJECT 횟수,
    warning_level별 빈도, forbidden(MED/HIGH) 차단 횟수

  2단계 — 정책 개입 효율 분석 (더 중요):
    - REJECT 발동 후 실제 진입이 없었고 그 방향이 손실이었는지
    - HALF 발동 후 진입했을 때 일반 진입 대비 손익 비교
    - REJECT가 수익 기회를 불필요하게 버렸는지 (과보수 판단)
    - LLM raw positive + REJECT → 결과가 어땠는지

구현 방향:
  - entry_gate_log + sim_trades 조인 집계 스크립트
  - 날짜별 비교 리포트 (터미널 또는 HTML)
전제조건: entry_gate_log + sim_trades 2주치 이상 필요 → 2026-04월 이후 권장
※ 이 분석 결과가 B-003(임계값 튜닝)과 A-003(Ambiguous v2) 설계의 입력이 됨
